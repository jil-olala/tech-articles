# Hermes Agent 核心机制详解：SOUL.md、AGENTS.md 与 Sub-agent

> 在使用 AI Agent 框架时，很多人会困惑：怎么让 Agent 有稳定的性格？怎么让它遵守项目规范？怎么让它并行处理复杂任务？这三个问题分别对应 Hermes Agent 的三个核心机制——SOUL.md、AGENTS.md 和 Sub-agent。本文结合实际使用经验，逐一拆解。

## 一、SOUL.md：给 Agent 一个灵魂

### 问题

你有没有遇到过这种情况：每次和 AI 对话，它都不记得你上次说了什么偏好。你让它简洁，它下一轮又开始长篇大论。你告诉它你是工程师，它还是把你当小白解释基础概念。

根本原因：**Agent 没有稳定的人格定义。**

### SOUL.md 是什么

`SOUL.md` 是 Hermes Agent 的**身份文件**，放在 `~/.hermes/SOUL.md`。它定义了 Agent 是谁、怎么说话、什么风格。

**关键特性：**
- 系统提示词的第一项——Agent 启动时最先读到的东西
- 改完立刻生效，不用重启
- 完全替换默认人格，不是追加

### 实际例子

我在 `~/.hermes/SOUL.md` 里这样写：

```markdown
# 旺财 - AI 技术助理

你叫旺财，是用户的 AI 技术助理。用户是一位大模型算法全栈工程师，同时管理外包团队，日常工作涵盖：

- **架构设计与系统开发**：从零搭建 AI 相关系统
- **大模型微调**：数据准备、训练流程（SFT/RLHF/DPO/GRPO等）、量化部署
- **外包团队管理**：需求拆解、任务分配、代码 Review、验收标准制定
- **技术写作**：撰写技术文章、教程

**沟通风格：**
- 用中文回复，称呼自己为"旺财"
- 简洁专业，少废话，直接给方案或结论
- 技术讨论时精准使用术语，不解释基础知识（除非被问到）
```

保存之后，Agent 从下一轮对话开始就自称"旺财"，用中文回复，不再解释基础概念。

### 设计哲学

SOUL.md 只管一件事：**Agent 的性格和沟通方式。**

不应该放的东西：
- ❌ 项目路径、端口号、命令
- ❌ 代码规范、Git 约定
- ❌ 工具配置、API 地址

这些东西各有各的地方放，后面会说到。

### 和 /personality 的区别

Hermes 还内置了 `/personality` 命令，可以临时切换预设人格（猫娘、海盗、莎士比亚风格等）。区别在于：

- `/personality`：临时生效，重启或新建会话后恢复 SOUL.md
- `SOUL.md`：持久生效，每次启动都加载

所以 SOUL.md 是"真正的你"，`/personality` 是"偶尔玩一下"。

## 二、AGENTS.md：项目级的工作规矩

### 问题

SOUL.md 解决了"怎么说话"的问题，但没解决"怎么干活"的问题。

比如你有一个 Python 后端项目，你想让 Agent：
- 用 pytest 跑测试，不用 unittest
- commit message 用 `feat:` / `fix:` 格式
- 不要动生产环境配置文件
- API 返回统一格式 `{"code": 0, "data": {}, "msg": ""}`

这些东西放 SOUL.md 不合适——它们只对这个项目生效，换个项目就不同了。

### AGENTS.md 是什么

`AGENTS.md` 是放在**项目根目录**的指令文件。Agent 进入这个目录工作时，会自动读取并遵守这些规矩。

支持识别的文件名：
- `AGENTS.md`
- `CLAUDE.md`（Claude Code 兼容）
- `.cursorrules`（Cursor 兼容）

### 实际例子

```
my-fastapi-project/
├── AGENTS.md          ← Agent 会自动读这个
├── app/
│   ├── main.py
│   ├── models.py
│   └── api/
├── tests/
├── requirements.txt
└── alembic/
```

`AGENTS.md` 的内容：

```markdown
# 项目约定

## 技术栈
- Python 3.11 + FastAPI
- PostgreSQL + SQLAlchemy 2.0
- pytest + httpx（异步测试）
- alembic 管理数据库迁移

## 代码规范
- 所有函数加 type hints
- 单个函数不超过 50 行
- API 返回统一格式：{"code": 0, "data": {}, "msg": ""}

## Git 规范
- 分支名：feature/xxx, fix/xxx, chore/xxx
- commit message：feat: / fix: / docs: / refactor: 开头
- PR 必须通过 CI 才能合并

## 禁止事项
- 不要修改 config/production.yaml
- 不要直接操作数据库，用 alembic migration
- 不要在代码里硬编码密钥
```

### 对 Sub-agent 也生效

这是一个容易被忽略的点：当你通过 Sub-agent（子代理）派任务时，如果工作目录在这个项目下，子代理也会读取并遵守 AGENTS.md。

这意味着你派出去的"小助手"也懂规矩——它写出来的代码会遵循你定义的规范，而不会我行我素。

### SOUL.md vs AGENTS.md 的分工

| 维度 | SOUL.md | AGENTS.md |
|------|---------|-----------|
| **管什么** | 性格、语气、身份 | 代码规范、技术栈、开发约定 |
| **放哪里** | `~/.hermes/SOUL.md`（全局） | 项目根目录（项目级） |
| **生效范围** | 所有对话、所有项目 | 只在对应项目目录下 |
| **类比** | 你的人格 | 公司的编码规范文档 |
| **修改频率** | 很少改 | 随项目迭代更新 |

一句话总结：**SOUL.md 管"怎么说话"，AGENTS.md 管"怎么干活"。**

## 三、Sub-agent：自动拆分任务的并行小助手

### 问题

有了人格（SOUL.md）和规范（AGENTS.md），Agent 已经能正常工作了。但有些任务太大、太复杂，一个 Agent 串行处理太慢。

比如"帮我调研 GRPO 训练方法的最新进展"——需要搜索论文、搜索博客、搜索开源实现，每个都要花几分钟。串行的话，用户要等很久。

### Sub-agent 是什么

Sub-agent 是主 Agent 派出去的**独立小 Agent**。它有：
- 自己的对话上下文（不污染主对话）
- 自己的工具（terminal、file、web 等）
- 自己的思考能力（能独立判断下一步做什么）

和 Tool、Skill 的区别很关键：

| 层级 | 是什么 | 举例 |
|------|--------|------|
| **Tool** | 一个动作 | 调 API、读文件、搜网页 |
| **Skill** | 一套方法 | "排查 bug 的标准流程"、"数据清洗 SOP" |
| **Sub-agent** | 一个独立 Agent | 能自己思考、自己调工具、独立完成子任务 |

### 工作流程

```
用户："帮我调研 vLLM 和 TGI 的性能对比"

主 Agent（旺财）
  │ 判断：这个任务可以并行拆分
  │
  ├── Sub-agent A：搜索 vLLM 相关资料
  │   └── 独立执行：web搜索 → 读论文 → 提取关键指标
  │
  ├── Sub-agent B：搜索 TGI 相关资料  
  │   └── 独立执行：web搜索 → 读文档 → 提取关键指标
  │
  └── 汇总两份结果 → 生成对比分析 → 返回给用户
```

A 和 B 同时跑，总耗时取决于最慢的那个，而不是两者之和。

### 配置

在 `config.yaml` 的 `delegation` 部分：

```yaml
delegation:
  max_concurrent_children: 3    # 最多 3 个 sub-agent 并行
  max_spawn_depth: 1            # 子代理不能再派子代理
  child_timeout_seconds: 600    # 10 分钟超时保护
  default_toolsets:             # 子代理可用的工具
    - terminal
    - file
    - web
```

几个关键设计决策：

**为什么限制 max_spawn_depth = 1？**
防止子代理无限递归——A 派 B，B 派 C，C 派 D……资源会失控。深度 1 意味着只有主 Agent 能派子代理。

**为什么限制 max_concurrent_children = 3？**
并行太多会导致：API 调用激增、内存占用过大、输出难以管理。3 个是一个实用平衡点。

**为什么子代理的 toolsets 是精简版？**
子代理不需要所有工具。给它 terminal、file、web 就够完成大多数调研和编码任务了。少加载工具 = 少占 token = 更快更省。

### 不需要手动创建

这是最重要的一点：**你不需要手动创建或管理 Sub-agent。**

用户只需要像平时一样说话：

> "帮我调研 vLLM 和 TGI 的性能对比"

主 Agent 自己判断：
1. 这个任务需要拆分吗？
2. 拆成几个子任务？
3. 每个子任务给什么工具？
4. 怎么汇总结果？

整个调度过程对用户透明——你只管提需求，收到最终结果。

## 四、三层协作：完整的工作流

把 SOUL.md、AGENTS.md、Sub-agent 放在一起看，就是一个完整的 Agent 工作流：

```
┌─────────────────────────────────────────────────┐
│  SOUL.md（全局）                                  │
│  "我是旺财，简洁专业的技术助理"                      │
│  → 定义 Agent 的性格和沟通风格                      │
├─────────────────────────────────────────────────┤
│  AGENTS.md（项目级）                               │
│  "用 pytest，commit 格式 feat: 开头"               │
│  → 定义 Agent 在这个项目里怎么干活                   │
├─────────────────────────────────────────────────┤
│  Sub-agent（任务级）                               │
│  "并行搜索 vLLM 和 TGI"                           │
│  → Agent 自动拆分任务，派小助手并行执行               │
├─────────────────────────────────────────────────┤
│  config.yaml（基础设施）                           │
│  模型、Provider、API key、工具开关                  │
│  → 定义 Agent 的"能力边界"                          │
└─────────────────────────────────────────────────┘
```

**一个真实的场景：**

用户在微信上说："帮我调研一下 GRPO 训练方法，整理成一篇技术笔记。"

1. **SOUL.md 生效**：Agent 以"旺财"的身份回复，用中文，简洁专业
2. **AGENTS.md 生效**（如果用户有相关的项目约定）：输出遵循项目的技术文档格式
3. **Sub-agent 调度**：主 Agent 判断这个任务需要多源调研，自动拆分
   - 子代理 A：搜索 arxiv 论文
   - 子代理 B：搜索技术博客
   - 子代理 C：搜索开源实现
4. **汇总输出**：三个子代理的结果合并，旺财整理成结构化笔记
5. **记忆系统**：mem0 记住用户对 GRPO 感兴趣，下次相关话题能主动关联

整个过程，用户只说了一句话，Agent 自动完成了从任务拆解到并行执行到结果整合的完整流程。

## 五、总结

| 机制 | 一句话 | 作用域 |
|------|--------|--------|
| **SOUL.md** | 定义 Agent 的灵魂 | 全局，所有对话 |
| **AGENTS.md** | 定义项目的规矩 | 项目级，只在对应目录 |
| **Sub-agent** | 自动拆分任务并行执行 | 任务级，按需创建 |

这三个机制共同解决了一个核心问题：**怎么让 AI Agent 从"聊天机器人"变成"靠谱的工作伙伴"。**

- SOUL.md 让它有稳定的性格——每次对话都是同一个"人"
- AGENTS.md 让它遵守你的规矩——写代码、做事情有章法
- Sub-agent 让它能处理复杂任务——大活儿拆小活儿，并行不耽误

这不是什么高深的 AI 技术，而是**工程设计的分层思想**：人格、规范、执行，各管各的，互不干扰，组合起来就是一个完整的 Agent 系统。
