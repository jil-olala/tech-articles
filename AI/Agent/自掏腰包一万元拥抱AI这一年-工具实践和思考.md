## 前言

我应该是比较早就开始关注大模型，并且也蛮愿意积极拥抱 AI 的同学。

产品体验方面，付费使用过的产品就包括但不限于 claude code max、gpt pro/plus、gemini pro、perplexity、cursor、lovable、gamma、windsurf、bolt.new、replit、seedance2.0…（至今已经撒币超万元）。

开发实践方面，从早期探索性的 AutoGPT、BabyAGI，到 LangChain/LangGraph 等编排框架和 Dify 等低代码平台的兴起，再到如今逐渐弱化框架，以 Agent + Skill/Tool 来完成复杂任务的新范式。

坦白讲，拥抱 AI 的这一路过程并不是那么顺利。每个时期的 AI 都有着不同的特点，很多时候当我费尽心思去钻研，自以为有点弄明白 AI 应该怎么玩的时候，基座模型和行业范式常常就会迎来颠覆式的变革。但是在经历这种不停摧毁和重建的过程中，还是沉淀了一些很有意义的东西。

本文主要分为两部分：第一部分偏务实，介绍工具、实践和方法论；第二部分偏务虚，分享碎碎念和对 AI 时代的思考。

## 01 工具、实践和方法论

### 1.1 把 Agent 用起来

#### 1.1.1 MAC 工具链分享

在大模型时代以前，三个屏幕就可以基本涵盖大部分工作所需。但现今我们有能力进行多个需求/项目的同时开发，传统桌面配置开始捉襟见肘。

核心工具链：

| 工具 | 性质 | 主要能力 |
|------|------|---------|
| Raycast | 闭源免费 | 应用快捷键启动、剪贴板历史 |
| AeroSpace | 开源 | 窗口自动分屏、工作区管理、应用自动归位 |
| Ghostty | 开源 | 多位知名 AI 技术大咖推荐的命令行客户端 |
| Yazi | 开源 | TUI 三栏文件浏览器、文件/图片预览 |
| lazygit | 开源 | 命令行 git 操作 |
| btop | 开源 | CPU/内存/磁盘/网络/进程实时监控 |
| fzf | 开源 | 历史命令搜索、文件搜索、目录搜索 |
| Claude Code、CodeBuddy 等 | 闭源付费 | AI 编码、Hooks 自动化、Skills 技能库、审计和执行 |
| Cockpit | 自研 | 跨机器任务状态仪表盘、Hooks 驱动生命周期自动同步 |
| tmux | 开源 | 远程终端复用、会话持久化、断线恢复 |

值得注意的两点：
- **最推荐的是 Aerospace 和 Raycast**，管理/切换工作区、快捷键打开应用、剪贴板历史是通用诉求
- **Cockpit** 是自研的跨机器 Agent 状态仪表盘，用于监控多个 Agent 在不同机器上的状态，避免因"等待审核"、"异常报错"长时间闲置

#### 1.1.2 一起来吃低垂的果实

**快捷指令**：让大模型自己开发 iOS 快捷指令，虽然仍然不稳定，但有 AI 可以持续维护。

**顺手提点 PR**：遇到开源项目问题，让 LLM 自主完成优化流程并提出 PR。

**打 Kaggle 比赛**：春节期间远程让台式机基于 Claude Code 分析比赛、训练模型、提交数据。约 4000 支队伍的比赛最高取得过榜第六的成绩。

### 1.2 从 Prompt Engineering 到 Harness Engineering

大模型应用范式沿四个阶段递进演化：

#### 1.2.1 Prompt Engineering：来时的路

最开始写 prompt，怎么措辞、怎么给例子、怎么引导思维链。但 Agent 在长时运行中面对的信息量是动态膨胀的，一个静态的 prompt 根本 hold 不住。

#### 1.2.2 Context Engineering：管好 Agent 看到的一切

Context Engineering 关注的是"Agent 每次推理时，整个信息环境长什么样"。这个信息环境包括系统指令、可用的工具定义、外部数据、对话历史、memory 等等。

核心思想：让 Agent 在每一步推理时，看到最精准、最少冗余的信息。上下文窗口是有限的，塞太多 Agent 会"迷路"（lost in the middle），塞太少又缺乏关键信息。

参考：
- Shopify CEO Tobi Lütke 帖子：https://x.com/tobi/status/1935533422589399127
- Anthropic 文章：https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

但 Context Engineering 解决了「Agent 看到什么」，没解决：**Agent 怎么知道你到底想要什么？**

#### 1.2.3 Spec-driven Development：先写契约，再让 Agent 动手

核心思路：别急着让 Agent 写代码，先写一份 spec。这份 spec 不需要是冗长的需求文档，而是一份清晰的契约——定义你要什么、不要什么、有哪些约束、验收标准是什么。

GitHub 开源的 Spec Kit（https://github.com/github/spec-kit）提供了一套比较成熟的工作流。通过 gated workflow 在每个阶段验证方向，看似变慢，实际大幅减少返工。

#### 1.2.4 Harness Engineering：给 Agent 搭一个约束体系

持续用 Agent 维护项目，会发现 Agent 会复制仓库中已有的模式，**包括不够好的模式**。命名风格漂移、重复函数出现在不同角落、架构约束被悄悄突破。Agent 的吞吐量远超人类，熵的增长速度也远超预期。

OpenAI 的实践：3 个工程师、5 个月、完全零手写代码，构建了约百万行代码的内部产品。团队的核心工作不是写代码，而是搭建 Harness。

**Harness 体系四个层面：**

1. **约束层**：用机械化规则代替口头约定。如果一条架构规则值得写进文档，那它就值得用 linter 来强制执行。

2. **文档层**：把 AGENTS.md 当目录而非百科全书。OpenAI 团队把 AGENTS.md 精简到约 100 行，只作为索引指向仓库中结构化的 docs/ 目录。"给 Agent 一张地图，而不是一本千页手册。"

3. **反馈层**：构建"犯错→修复→沉淀"的飞轮。每当 Agent 犯了一个错误，就工程化一个方案确保它不会再犯。当 Agent 卡住时，从不选择"再试一次"或人工介入，而是诊断"缺了什么能力"，然后让 Agent 自己把缺失的能力构建回仓库。

4. **清理层**：自动化对抗熵增。把"黄金原则"编码为仓库级的规则，用后台 Agent 定期扫描偏差、自动提交清理 PR。把技术债变成每天的小额偿还。

参考：
- OpenAI 文章：https://openai.com/zh-Hans-CN/index/harness-engineering/
- Octopus Deploy：https://octopus.com/devops/continuous-delivery/harness-engineering/

### 1.3 让 Agent 替我学习

#### 1.3.1 「古法学习」行不通了

痛点：
- 技术迭代过快导致的信息量数以倍增，几乎不可能有足够时间收集和钻研
- 技术范式完全没有稳定，各种分享良莠不齐，很难确认什么是真正有效的最佳实践
- 大模型时代的 AI 应用领域几乎是所有使用 AI 的人类一起在迭代，无分领域、无分文理、无分老少

#### 1.3.2 让 Agent 帮我学，帮我用

**核心态度：既然我学习不过来了，那 Agent 帮我学习吧；既然我应用的比较慢，Agent 帮我应用。**

把自己从信息采集的第一线撤出来，让 Agent 去做每日的资讯扫描和筛选，只看提炼后的"精华版"。Agent 在采集过程中积累的知识会反哺到它自身的工作体系，使它在下一次被调用时比上一次掌握了更多业界前沿的优秀实践和解决方案。

知识管理基于 Claude Code 结合 Skills 体系和 multi sub-agent：

| Skill | 层级 | 功能 |
|-------|------|------|
| ai-news | 采集层 | 每日 AI 新闻聚合筛选。11+ 并行源（HN/HF/GitHub/Reddit/36Kr/量子位等），智能评分 0-10（跨源共振+3、突破+2），≥4 分入选 |
| podcast-batch | 采集层 | 批量转录+分析近期更新播客，腾讯 ASR 10h/月免费额度 |
| web-collect | 采集层 | 从指定网页/站点采集整理信息，支持 md/JSON/CSV 输出 |
| research | 采集层 | 深度调研指定主题，多源采集+交叉验证，结构化报告 |
| ai-practices | 提炼层 | 全自动提取可复用 AI 最佳实践，严格准入（需 URL、≥50 字、可复用非一次性新闻） |
| workspace-evolve | 应用层 | 审计工作空间配置并建议优化，对比官方+社区最佳实践 |
| doc-writer | 应用层 | 撰写结构化文档，支持技术方案/指南/分析/总结等类型 |
| podcast-script | 应用层 | 从素材生成播客对话脚本并合成音频，用 doubao 中文语音+coze 工作流 |
| tool-builder | 应用层 | 构建实用工具/脚本，需求分析→技术选型→实现→测试→归档 |
| create-shortcut | 应用层 | 生成 macOS 快捷指令(.shortcut) |
| generate-tests | 应用层 | 生成全面测试套件，覆盖单元测试、集成测试和边界用例 |

核心态度：**在一个知识和范式都在高速变化的时代，与其追求"深入理解每一个东西"，不如追求"快速沉淀和验证每一个有价值的东西"。**

## 02 碎碎念、思考和暴论

### 2.1 这实在是一篇太不 AI Native 的文章

撰写这篇文章本身是最不 AI Native 的事情。知识整理和分享是大模型非常擅长的事情，而且本文提到的绝大部分内容在个人工作空间都有痕迹可以追寻。

还有一件很不 AI Native 的事：这篇讲 AI 的文章第一节居然推荐的是 MAC 电脑的工具链。所谓的 AI Native 可能总不会还需要程序员苦哈哈熟悉一大堆工具、记忆一大堆快捷键。但就个人体感来说，Claude Code 仍然是我认为当下最好的 Agent 工具，围绕用好 Claude Code 来做事情，可能是当下对于程序员投入产出比最高的事情之一。

### 2.2 与 AI 做好朋友

Andrej Karpathy 提出的 "Jagged Intelligence"（锯齿智能）概念：LLM 的能力分布跟人类完全不同。大模型有些事做得惊人的好，有些事错得离谱，而且哪些行哪些不行并不显而易见。

Karpathy 的解决方案：**你可以随着使用逐渐建立起直觉。** 持续使用是最好的老师，在与 AI 沟通一万句以后也许就会发现很多困惑自然而然迎刃而解。

最简单高效的方法：**「用最好的模型」+「持续与 AI 交流」**

参考：https://x.com/karpathy/status/1816531576228053133

### 2.3 讲一下用 AI 的苦日子

在去年年中以前，使用顶级大模型需要钻研的是如何越过被封禁的网络、解决海外信用卡和手机号的限制、想着怎么薅羊毛降低成本。

METR 的实验（https://metr.org/blog/2025-07-10-early-2025-ai-experienced-os-dev-study/）明确表示 25 年前期使用 AI 编程反而可能会降低效率。

但大模型能力本身已经经历飞跃式的进步，**AI 正当时。**
